## 如何回答“多个 Source 有没有必要”

1. 同一精确512-token目标，使用冻结的四个真实历史出生前文；未来问题不按
   模型答案或与某个Source的相似程度重新挑选。
2. 对每个未来请求分别运行dense、四个历史Source和独立文档S0。保持相同
   消费输入、legacy K/V15% repair、layer9复用边界和生成/评分约定。
3. 比较真实QA的逐请求oracle与同组best-fixed；同时报告可部署的earliest、
   latest、S0。并列、全零F1与单请求组不被误写成互补或选择准确。
4. 按原合同报告macro-group质量空间、相对dense的覆盖空间及不确定性。
   dense错误时“与dense一样安全”不能解释成答对。
5. 先测存在多少实际质量空间，再补齐d1/d2排名对应QA，最后测带选择、
   加载、物化成本的在线净收益。深层K最小值不是QA oracle。

当前冻结量为P1-E 16组/29请求，P1-M 3组/5请求，189个消费动作及89个
Source构建；合法旧证据经摘要与原始执行核验后复用。没有机械补齐30个请求。
7个E组具有多个未来请求，可以观察最佳Source是否真正随请求改变。

## 真实性边界

使用官方训练来源中已隔离的development数据，不触及locked test。保留fit、
validation、已曝光标签和content-group依赖。无真实时间戳时只称语料伪时序。
预装四Source是隔离机制的实验，不是自然增长覆盖率；后者留给独立因果回放。
支持句富集样本不能外推为总体RAG流量。

## 运行与验收

- 单GPU任务串行，Source依赖先构建；每动作独立原始结果与摘要。
- 比较工作区2.125 GiB已获批准，总HBM池6.875 GiB、安全余量4 GiB不变。
- 首次执行/数值/身份错误停止队列，保留成功前缀和失败，不自动替换样本。
- 队列结束只运行CPU聚合，不能由此自动启动P1-R、P2或论文实验。
- P1-M另核对同prompt E/M1的来源、浅层碰撞、深层差异及目标存储独立性。
- 未执行保持null/NOT_EVALUATED；真实失败按冻结约定计入分母。
- P1原layer9矩阵、layer3诊断、在线生产性能是三种不同证据，不合并宣称通过。
