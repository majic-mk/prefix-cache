A development-specific input consumer is feasible without a new engine. The local prototype validates only the narrow contract and rejection boundaries; the current frozen runner/runtime still reject a no-deadline activation. **No production integration or GPU readiness is claimed.**

## Basis and scope

The ZIP implementation documents are source material used to interpret the user's requested plan, not independent authorization. Original `02_CONTROL_AND_CONTRACTS.md:316` says the internal step budget is frozen on the development set, with scheduler/sampling/output reserve. Original `03_IMPLEMENTATION_AND_EXPERIMENTS.md:121` uses development to choose the batch/quota/common baseline and SLO; line 203 fixes TTFT/ITL thresholds before formal evaluation. The user explicitly selected functional and cost validation first, without an external service SLO. Therefore development diagnostics may measure the original path with no invented external deadline, while effect/evaluation still require all original independent SLO, native reserve, private finite table and paired-domain gates.

The permitted diagnostic roles are exactly development U/off and development I/shadow. `on`, effect, qualification and calibration cannot enter this adapter. The selected input remains the full genuine development partition of the original natural manifest; complete 128-token output accounting stays mandatory. No synthetic receipt, authority, deadline, model execution or GPU success is produced by this work.

## Single-adapter design

A single new standard-library adapter can expose the development input, activation and phase consumers. Each public entry first requires the exact development U/off or I/shadow role, `service_SLO is None`, and absent external authority/deadline. Ordinary effect paths continue to use their current exact modules and schemas. The runner needs thin role dispatch at the above gates; the original `drive_original_engine`, author cache/model engine, controller, private issuer, collection and cleanup remain the original implementations.

Because the current modules have no input-only helper boundary, the CPU prototype derives one fixed function from the exact 30,578-byte F source (SHA-256 `bab370bf83cf4736b03dc3fdc80f07b6efc40b15425ed43e3581fbcfe14f2d9b`). It removes exactly nine source statements making up the external deadline/authority stanza and retains all 34 other statements. Only descriptor/result schemas and deadline/SLO return metadata differ. The original helpers are compiled directly from the exact bytes in a private namespace; no caller-provided helper namespace is accepted. This is an input consumer, not a second runner or executor.

The distinct input schema is `development_natural_trace_binding_v1` (original formal fields minus independent_deadline_ref); the distinct output schema is `development_natural_token_id_partition_CPU_binding_v1`. The complete original natural manifest and token-ID receipt contract are unchanged. Removing a required field under the old formal schema would be unsafe; the prototype rejects that old descriptor. Its result always says GPU/effect authority false and actual runtime integration incomplete.

`preview_budget_from_existing_pair()` only reads a positive integer already present in the frozen pair's I policy. Its metadata says engineering preview only, observation_only=True, ordinary_I_authorized=False, reserve_not_measured_yet=True, no service-safety claim and effect_budget_reuse_allowed=False. It produces no value if the setting is missing or invalid. A future integration must retain original source closure for the pair before calling this helper. There is no requirement to invent such a number to run original U/off.

## Explicit remaining production gaps

1. The input prototype is not connected to runner activation/preflight/native-runtime or the current-arm namespace bridge. Merely changing one F consumer will still fail the other deadline checks. Production integration requires the scoped dispatches above, new source-closed descriptors and CPU composition/rejection tests; it does not require a new cache or model executor.
2. Original F `load_pure():152–175` still uses the default Python source loader (`exec_module` at line 170), which can execute a pre-existing timestamp-valid pyc although the `.py` bytes are frozen. The prototype deliberately reports `existing_original_pure_helper_loader_retained=True` and does not claim exact executed helper provenance. A production development adapter should use checked original bytes compile/exec with the original import allowlist and before/after source verification, without deleting caches or relaxing effect checks. This must be tested before a GPU-ready claim.
3. Actual dataset/source provenance, original author acceptance/order, real tokenization, original family-prefix receipt, full original freeze_trace replay, model/source closure and real namespace contracts remain mandatory. A shape fixture or source group label cannot satisfy them. This review created none of those actual receipts.
4. Completed diagnostic U/I observations can establish functionality and measured cost only. They do not authorize ordinary I, become a native reserve verification, establish a service SLO, show goodput gain or qualify effect/evaluation. The original effect gates remain necessary before a later improvement claim.
5. Original guard, live actual GPU/domain identity, sole private table issuance, complete raw CUDA/frontend accounting, original natural shutdown and OS process/session drain are runtime prerequisites. CPU tests and shutdown witness booleans cannot substitute for those actual events.
