# Bounded P0 lineage continuation

This action closes the G0 → G1 publication → later G1 consumption → G2 rejection
test gap. It is **not** a production economic-admission test or a natural-workload
opportunity measurement. The previous teacher/reference T20/T21/T31 outputs
remain non-publishable. Their successful comparisons do not prove this chain.

`controlled_lineage_birth` is explicit in the signed, bounded P0 manifest:

- Controlled input, one ordinary greedy output token; no teacher, logit trace,
  extra full-prefill, Prefix shadow, or native dense-continuation fallback.
- Unique, causally visible preregistered upstream parent; actual K-only receipt
  must verify all eligible sources, its winner, and the unchanged threshold.
- Target captures every row of every actual block in that same execution.
- Existing SSD lease, HBM reservation, normalized K/V fixed15 repair support,
  ready-event checks, and existing CacheBlend layer executor remain in force.
- The named recipe commit is not FinalCommitAdmission: record
  `economic_admission_evaluated=false`,
  `production_reuse_commit_observed=false`. It must not produce an economic
  `passed=true` value or manufacture a cost table.
- Post-answer publication uses authentic comparison receipts and the existing
  durable isolated P0 store. The birth snapshot cannot see its child.
- G1 must publish and remain readable to a subsequent request; later use of G1
  must give the full downstream target G2 and reject it before publication.
- Execution, failure and cleanup records are retained. A stale/failed lease,
  incomplete capture, nonfinite state, failed fence, or missing winner is a stop,
  not permission for another Source or a threshold change.

The planned continuation is three actions in a **new empty isolated pool**:
G0 upstream birth; G0 upstream reuse with full target G1 birth; G1 upstream reuse
with full next target G2 rejection. Exact concrete tokens, source references,
depth, model, code bytes, limits and current authorization are bound before GPU
execution. Source IDs produced by earlier actions resolve only forward in time.
No P1 or full experiment follows automatically. A fresh snapshot does not extend
the user's original two-hour authorization window.

CPU tests validate contracts, real local storage and fake-block hooks only.
Real-model/GPU status remains NOT_RUN until a new digest-bound batch succeeds.
