# Independent C5 native-cost CPU preparation acceptance

This review is confined to the new native-cost preparation directory. It does not
authorize a GPU run, instantiate a model, issue a native cost receipt, change an
old source file, or turn earlier C4/v6 results into C5 qualification.

## Contracts that can be checked without a GPU UUID

- A draft with `gpu_uuid: null` is explicitly a CPU preparation document. It is
  not an original native plan, runtime configuration, permission scope, job,
  valid receipt, reservation, or measured cost table. Rendering must preserve
  these distinctions and must not invent a device UUID.
- C5's real reactor reference belongs to common sources. The actual collector
  appears exactly once among overlay sources and equals the plan's collector
  reference. Files are bound by project-relative path, size, and SHA, including
  new serializer/factory/launcher code and original estimator dependencies.
- Original policy and bridge bytes are unchanged. The policy's exact-type check
  resolves the same canonical `prefix_io_control.p4_single_file_receipt`
  module/class as the prepared factory; a same-named class from a second module,
  a dict, a private preparation record, or an inherited C4 receipt cannot prove
  actual integration.
- The finite geometry stays at six fresh windows in AB/BA/AB order, two
  calibration pairs and one holdout, 129 prompt/128 cached/128 output tokens,
  selected offset 16, one 917504-byte SSD read, accepted-parent cap 8, and
  bridge=None for common calibration. The original formula and A-only budget
  must remain unchanged. Holdout and warmup values cannot fit the upper bound.
- CPU fixtures may exercise the original serialization and numerical code and
  reject malformed evidence. They must be labelled synthetic and return no
  effective cost, native receipt, or native/production/full-runtime qualification.
- Every public acquisition/configuration/plan/scope/job/issuance entry point is
  blocked before model imports, native calls, filesystem writes, process launch,
  or ledger changes. In particular, CLI help or an old completed scope is not a
  route around an entry-point block.

## Required counterexamples

The independent suite targets real call sites and source contracts, as well as
helper-level validation: wrong/old reactor source, collector swapped into common,
duplicate collector, mismatched source hash, legacy v6 job/scope, unknown or
invented GPU UUID, old raw receipts, canonical-module split identity, changed
policy/bridge bytes, and attempts to invoke blocked entry points with valid-looking
old arguments. A fixture's apparent PASS must never be sufficient for issuance.

## Evidence and limits

The runner uses explicit project/candidate/original/native/preparation roots and
an externally supplied source-lock SHA. It reports dynamic source counts and
the complete before/after source references, actual test/failure/error/skip
counts, location, and forbidden model-module imports. GPU runs, model loads,
new jobs/scopes and effective costs remain zero/false/null as appropriate.

No CPU contract result proves that new C5 common costs cover the on-only policy,
notification attachment or queue observer. The earlier 73.6% synthetic CPU
reduction does not cover this full preparation path. Actual device binding,
raw six-window calibration, off/shadow/on lifecycle, and cost coverage remain
separate later work under explicit authorization and the unchanged budget.
