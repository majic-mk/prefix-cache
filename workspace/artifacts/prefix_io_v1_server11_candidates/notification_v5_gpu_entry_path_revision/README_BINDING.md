# C5 bounded native common-cost GPU entry

This separate path compatibility revision accepts the relative `Path` produced
by the real native CLI's `argparse --config` option as a project-relative POSIX
path. Contained absolute paths remain accepted; foreign absolute paths,
traversal and symlinks remain rejected. CPU tests exercise the actual argparse
input shape without creating any valid GPU configuration or native receipt.

The previous device revision's one authorized guard attempt ended with exit 2
at configuration parsing, before model loading or any experimental window. That
attempt's source, authority, log and budget evidence remain unchanged. Its
one-attempt authorization is consumed; this revision prepares a new concrete
context and requires the next bounded execution authorization. CPU path tests
cannot establish successful GPU execution or native cost qualification.

This revision makes the real native GPU entry reachable only after actual site
resource observation, a source/UUID/job-specific direct human grant, and
complete byte-frozen assets. CPU preparation produces an explicitly UNBOUND
template. It never writes an effective permission, configuration, scope, native
receipt, cost bound or GPU-qualified result. The orchestration task records the
actual direct human scope for this source/UUID/job in the live binding.
Preparation instructions alone do not create execution authorization.

The common compatibility fix in this separate revision recognizes any allocated
numeric NVIDIA character device (for example `/dev/nvidia5`) together with the
character control node. It does not assume the assigned GPU has host ordinal
zero. UVM/capability nodes, regular files and symlinks cannot satisfy this check.
Single-UUID telemetry, VRAM, empty compute process list and every resource floor
remain unchanged. Pure CPU device-metadata tests do not prove a GPU run succeeded.
The previous revision remains unchanged.

The live context must observe one visible NVIDIA GPU, at least 28,000 MiB free
VRAM, no existing compute application, readable CPU quota/counters with at least
one effective CPU core, 32 GiB available host/container memory, and 10 GiB PRIMARY
free space (2 GiB reserved plus the unchanged 8 GiB floor). Unknown CPU quota is
rejected; a readable unlimited quota is allowed subject to affinity. Resource
readiness alone grants no experiment or performance qualification.

Use the exact commands recorded in the UNBOUND review template. `context` first
checks actual resources, original budget and unused label. Only then does it
freeze the original 4,655 references and added C5/code/input provenance. The old
lock is source ancestry, never authority. No model or cache bytes are copied.
The 24 existing model-produced KV inputs and their three producer references
are byte-pinned. The original guard SHA is fixed in `gpu_entry_binding.py`.

The orchestration task records the bounded execution authorization for this new revision
in `HUMAN_GPU_GRANT.json` with its direct instruction and scope plus the context,
revision hash, UUID, label, one attempt, six processes, and 1,200 plus 20 seconds.
No CLI flag or function creates that human grant. `bind` verifies it and creates
a separate effective JSON/YAML permission. The original base permissions remain
unchanged. No download, rental, payment, system/driver modification, auxiliary
storage, deletion, budget enlargement, automatic retry or foreign UUID is
permitted.

`REVISION_SOURCE_LOCK.json` freezes source and existing assets. The configuration
refers to `SITE_SOURCE_LOCK.json` by path, so the final site lock can include the
configuration, binding, live context, human grant, effective permission and
revision lock without a self-referential hash. The final site lock must contain
the exact union; omission, duplicates, added authority and drift are rejected.
Duplicate JSON/YAML keys, nonfinite values, boolean numeric aliases, traversal
and symlinks are rejected.

The controller fully hashes all frozen bytes before plan preparation, again
immediately before launch, and after the original guard completes and drains.
Native execution checks the lock, the immutable before/launch proof, current
entry/collector bytes, all site authority files and the original guard's actual
session. It does not repeatedly hash model weights inside timed frames. The
full after proof is required before final canonical verification. Launch intent
pins both the plan and its plan-reference container. Native child sessions must
match the original guard, visible UUID and process group. At most one second of
metadata polling covers the original guard publishing its newly created session;
it never restarts a GPU process.

The original `run_gpu_stage.py` alone owns durable budget reservation, the job
limit, shutdown, session cleanup and actual elapsed-time accounting. Completed
qualification requires one unique successful ledger event, strict typed exit
flags, real reservation/session IDs, an empty drained session, source closure
before and after, and accounting equal to the prelaunch usage plus actual elapsed.
The native serializer separately retains the original six-window numerical and
holdout verifier. A launcher receipt or CPU test is never a native-success proof.

CPU tests exercise path normalization, byte/reference drift, old and UNBOUND
authority rejection, resource floors, strict JSON and types, no-card context
rejection and template-only preparation. Numeric resource fixtures are only
function inputs; they are never serialized as a live context or GPU receipt.
The source-locked CPU runner reports zero GPU runs and all GPU/cost qualifiers
false. Real normal-model off/shadow/on integration follows a verified native
common receipt in a subsequent authorized revision.
